## Detailed Findings

### 1. [P1] Semantic colors produce unreadable text combinations

**Category:** Accessibility / Theming  
**Evidence:** Browser-verified dark header; source-verified completion badges.

**Locations:** [dark primary token](/Users/eppedema/Documents/workspace/unmarker.it/src/index.css:109), [header descriptor](/Users/eppedema/Documents/workspace/unmarker.it/src/components/Header.tsx:24), [completion badge](/Users/eppedema/Documents/workspace/unmarker.it/src/components/PipelineSteps.tsx:108).

| Pair | Contrast | Interpretation |
| --- | --- | --- |
| Light primary on light page | 5.277:1 | Passes normal-text AA |
| Dark primary on dark page | **2.702:1** | Fails even large-text AA |
| Dark primary on dark card | **2.338:1** | Fails text thresholds |
| Completion rose on white | **3.755:1** | Fails normal-text AA before the badge's tinted fill is considered |
| Light primary-foreground on primary | 5.072:1 | Primary button text passes |
| Dark primary-foreground on primary | 6.968:1 | Dark primary button text passes |

The dark header visibly uses the failing pair for both the product descriptor and “100% client-side.” The completion badge uses small text in the rose color on a rose-tinted light surface, so its contrast is below the 4.5:1 requirement as well.

**Impact:** Users with low vision have difficulty reading important identity, privacy, and completion information. Passing button contrast does not make the same primary color safe as text on the page.

**Standard:** [WCAG 1.4.3 Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): 4.5:1 for ordinary text; 3:1 for qualifying large text.

**Recommendation:** Define or choose contrast-safe foreground variants for accent text and completion labels. Preserve the brand hues while separating fill and text use cases; check actual tinted backgrounds in both themes. Avoid globally brightening the primary fill without rechecking its pale button text.

**Suggested command:** `$impeccable harden`.

### 2. [P1] Progress bars drop their value and lack accessible names

**Category:** Accessibility / Implementation Integrity  
**Evidence:** Source-verified, including the installed Radix implementation.

**Locations:** [Progress primitive](/Users/eppedema/Documents/workspace/unmarker.it/src/components/ui/progress.tsx:6), [provenance score](/Users/eppedema/Documents/workspace/unmarker.it/src/components/AnalysisPanel.tsx:64), [pipeline progress](/Users/eppedema/Documents/workspace/unmarker.it/src/components/PipelineSteps.tsx:66).

The wrapper destructures `value` out of its props and uses it only for the indicator's CSS transform. It never passes `value` to `ProgressPrimitive.Root`. Radix consequently receives an indeterminate value and omits `aria-valuenow`, even when a definite percentage is drawn. Both callers also omit an accessible label or label association.

**Impact:** Assistive-technology users encounter unnamed, indeterminate progress instead of the meaningful score or step percentage visible on screen.

**Standard:** [WCAG 4.1.2 Name, Role, Value](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html).

**Recommendation:** Forward `value` to the Radix root and associate every instance with its localized score/step label. Consider a meter rather than progressbar semantics for the static provenance score. Keep the accessible and visible values synchronized.

**Suggested command:** `$impeccable harden`.

### 3. [P1] Final verification status has no announcement mechanism

**Category:** Accessibility  
**Evidence:** Source-verified; not tested with a speaking screen reader.

**Locations:** [WorkflowSummary](/Users/eppedema/Documents/workspace/unmarker.it/src/components/WorkflowStatus.tsx:20), [postflight completion](/Users/eppedema/Documents/workspace/unmarker.it/src/hooks/useImageWorkflow.ts:258), [pre-verification success toast](/Users/eppedema/Documents/workspace/unmarker.it/src/hooks/useUnmarkPipeline.ts:195).

The visible summary changes phase text inside ordinary divs and spans. It has no status role or live region. The pipeline success toast is emitted before postflight verification starts; normal verification completion subsequently changes state without a corresponding announcement. There is no focus movement to the completed result.

**Impact:** A screen-reader user may hear that processing finished but receive no notification that verification has completed and the final result is ready.

**Standard:** [WCAG 4.1.3 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

**Recommendation:** Keep a persistent, localized `role="status"` / polite live region for phase transitions and final verification outcome. Announce meaningful stages and completion, not every percentage tick. Preserve existing error-alert behavior.

**Suggested command:** `$impeccable harden`.

### 4. [P1] Homepage promises exceed the implementation's guarantees

**Category:** Implementation Integrity  
**Evidence:** Browser-visible copy checked against local processing and analytics code.

**Locations:** [English introduction](/Users/eppedema/Documents/workspace/unmarker.it/src/i18n/resources/en/homepage.ts:33), [verification limitation](/Users/eppedema/Documents/workspace/unmarker.it/src/i18n/resources/en/workflow.ts:69), [analytics initialization](/Users/eppedema/Documents/workspace/unmarker.it/src/lib/analytics.ts:155), [noise processing](/Users/eppedema/Documents/workspace/unmarker.it/src/lib/pipeline.ts:112).

The introduction says invisible watermark signals are neutralized, that no data leaves the device, and that processing avoids visible degradation. Elsewhere the app correctly states that hidden-watermark removal cannot be independently verified. Processing applies geometric changes, noise, and lossy JPEG encoding. Configured production analytics can also send usage/error events; localhost explicitly disables that instrumentation.

**Impact:** Users can mistake an experimental disruption result for independently proven removal, assume lossless quality, or misunderstand the scope of the image-privacy promise.

**Standard:** Product truth and consistency with `PRODUCT.md`; not a WCAG finding.

**Recommendation:** Scope privacy copy to image files/pixels, describe hidden-watermark processing as disruption without a removal guarantee, and acknowledge possible quality changes. Review both locales and metadata copy together. Preserve the factual distinction between local image processing and optional analytics.

**Suggested command:** `$impeccable clarify`.

### 5. [P2] The upload area nests a button inside a button role

**Category:** Accessibility  
**Evidence:** Browser accessibility tree, keyboard focus, and source.

**Locations:** [outer upload control](/Users/eppedema/Documents/workspace/unmarker.it/src/components/ImageUploader.tsx:112), [nested Choose Image button](/Users/eppedema/Documents/workspace/unmarker.it/src/components/ImageUploader.tsx:170).

The large card is focusable with `role="button"`, and it contains a second native button for the same action. The observed accessibility tree exposes both, with the outer button's name incorporating the title, description, file limits, and privacy text. Keyboard navigation visits both controls.

**Impact:** Users encounter redundant stops and a long outer control name; nested interactive semantics are unreliable across assistive technologies. The outer control does receive a native focus outline, so “no keyboard focus” would be an incorrect finding.

**Standard:** [WAI-ARIA button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/) and accessible control structure. A blanket keyboard-operability failure was not established.

**Recommendation:** Make the drop region a non-button container with a single native file-selection action, or implement one native interactive element without interactive descendants. Associate supporting instructions as a description rather than incorporating the whole region into its name.

**Suggested command:** `$impeccable harden`.

### 6. [P2] Motion preferences have no intentional alternative

**Category:** Accessibility  
**Evidence:** Source-verified.

**Locations:** [smooth scrolling](/Users/eppedema/Documents/workspace/unmarker.it/src/index.css:141), [result entrance animation](/Users/eppedema/Documents/workspace/unmarker.it/src/WorkflowApp.tsx:259), [spinner](/Users/eppedema/Documents/workspace/unmarker.it/src/components/ui/spinner.tsx:11).

The app uses smooth scrolling, a 500ms slide/fade entrance, spinning indicators, and pulsing skeletons. No application `prefers-reduced-motion` alternative was found. No flashing or motion that blocks task completion was observed.

**Impact:** Motion-sensitive users cannot opt out of nonessential movement through their system preference.

**Standard:** [WCAG 2.3.3 Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) is AAA; absence of this preference handling alone is not claimed as an AA failure.

**Recommendation:** Remove positional entrances and smooth scrolling under reduced motion; preserve state feedback through static labels and restrained non-spatial changes. Avoid a global near-zero-duration reset that destroys useful feedback.

**Suggested command:** `$impeccable animate`.

### 7. [P2] Several touch targets are smaller than the audit's 44px target

**Category:** Responsive Design / Accessibility  
**Evidence:** Browser-measured controls and source.

**Locations:** [language selector](/Users/eppedema/Documents/workspace/unmarker.it/src/components/LanguageSwitcher.tsx:37), [button size definitions](/Users/eppedema/Documents/workspace/unmarker.it/src/components/ui/button.tsx:25), [upload action](/Users/eppedema/Documents/workspace/unmarker.it/src/components/ImageUploader.tsx:170).

- At 320px, language links are approximately 36.91 × 26.25px and 71.52 × 26.25px.
- The upload button is 37.5px high; its surrounding clickable region improves pointer access but creates the separate semantics issue above.
- At desktop sizing, footer button links are 40px high and the theme toggle is 36 × 36px. Their rem-based sizes shrink further with the 15px mobile root.

**Impact:** Small, adjacent language controls and the theme toggle demand more precise tapping than necessary.

**Standard:** The skill uses 44 × 44px as its touch-usability target. [WCAG 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) uses 24px with exceptions; these measurements alone do **not** establish an AA target-size failure.

**Recommendation:** Give coarse-pointer controls a minimum 44px hit area independent of the responsive root font size, preserving the square visual identity. Prioritize language selection and the theme toggle.

**Suggested command:** `$impeccable adapt`.

### 8. [P2] Artificial waits delay every successful processing run

**Category:** Performance  
**Evidence:** Source-verified deterministic delay, not a measured end-to-end benchmark.

**Location:** [Shake / Stir / Crush orchestration](/Users/eppedema/Documents/workspace/unmarker.it/src/hooks/useUnmarkPipeline.ts:166).

Each of the three stages awaits `delay(500, signal)` before doing its work. These sequential timers add at least 1,500ms to a successful run and reprocess, regardless of image size. The waits do not implement necessary computation.

**Impact:** Users wait longer before results are available, especially for small images that would otherwise finish quickly.

**Standard:** Performance/usability; no WCAG claim.

**Recommendation:** Remove the fixed delays or replace them with a minimal scheduling yield where needed to paint progress. If minimum stage visibility is a product requirement, separate its presentation from the time at which a finished result becomes usable.

**Suggested command:** `$impeccable optimize`.

## Patterns and Systemic Issues

1. **Visual and accessible state diverge.** Progress is drawn without transmitting its value; final phase text changes without an announcement. Address these at the primitive and workflow boundaries.
2. **A single accent is used for incompatible contrast roles.** A successful filled button does not imply readable foreground text using the same color.
3. **Small rem-based controls shrink with the mobile root.** Minimum hit areas need their own rule.
4. **Top-level claims are stronger than result-level explanations.** Keep homepage, localized copy, and verification wording aligned.

## Positive Findings

- The design is coherent with the documented system; no generic redesign is warranted.
- The sampled English and Chinese layouts adapt without page-level horizontal scrolling.
- Language navigation has a label, real links, `lang`/`hreflang`, and current-page semantics; the document language updates correctly.
- Keyboard users can reach the file selector and its action, and the outer upload region has a visible native focus outline.
- Text alternatives are present for image previews, and the JPEG-quality slider has a localized accessible label.
- Working images are contained rather than cropped in the comparison UI.
- The main workflow is lazy-loaded; the footer is deferred; image analysis uses a Web Worker. The noise loop yields between bounded chunks and supports cancellation.
- Main text contrast is strong: muted text measured 7.730:1 on the light page and 9.815:1 on the dark page.
- No broad `will-change` usage or large decorative blur effects were found in the inspected implementation.
